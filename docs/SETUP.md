# Setting up the admin (one time, for the web lead)

The website runs on three free services. Each keeps one job:

| Service | Job | Holds |
|---|---|---|
| **Vercel** | Serves the website to visitors and rebuilds it after every Publish | The built site, CONTENT_EXPORT_URL and CONTENT_EXPORT_TOKEN |
| **Render** | Runs the admin server (`backend/`) that the `/admin` page talks to | Every secret: database link, export token, rebuild link |
| **MongoDB Atlas** | The database: accounts, every published release, photos, activity log | Only Render can connect to it |

GitHub holds only the code. The admin never uses GitHub tokens and never makes commits.

### Who owns what

| Thing | Account |
|---|---|
| **GitHub** (the code, private repository) | the web lead's personal account — the club can be given the code later |
| **Vercel** and **Render** (hosting) | the **club email**, so the chapter keeps the site when the web lead leaves |
| **MongoDB Atlas** (the database) | currently the web lead's personal account; can be moved to the club email later |

Because the repository is **private and owned by a personal GitHub account**, the GitHub account you connect inside
Vercel and Render must be that same personal account — a club Vercel/Render account cannot see the repository on its
own. So: sign up for Vercel and Render **with the club email** (not "Continue with GitHub"), then, inside each one,
connect GitHub and sign in with the personal account that owns the repository, giving the Vercel/Render GitHub App
access to **only** this repository. The club owns the hosting; the code link runs through the web lead's GitHub until
the repository itself moves to a club account.

Plan for about an hour. Turn on 2-step login for every account, keep every password
and token in the club's password manager, and **never add a payment card** anywhere: without a card, going over a free
limit pauses a service instead of charging the club.

Before you start, the code you want live must be on the `main` branch on GitHub.

## 1. MongoDB Atlas (the database)

1. Sign up at <https://cloud.mongodb.com> with the club email. Turn on 2-step login (your name, top right →
   **Account** → **Security**).
2. Create an organisation and a project named `ieee-cis`.
3. **Create the free cluster:** **Clusters** → **Create** (or **Build a Database**) → choose **M0 (Free)** → provider
   **AWS** → region **Mumbai (ap-south-1)**. If Mumbai isn't offered for free, pick the nearest free region
   (Singapore is fine too). Name it `ieee-cis-app` → **Create Deployment**. If a "Connect" window opens, close it; the next
   steps do the same thing.
4. **Database user:** **Security** → **Database Access** → **Add New Database User**
   - Authentication: **Password**. Username `cis-app`. Click **Autogenerate Secure Password**, then copy it into the
     password manager.
   - Database User Privileges: **Specific Privileges** → **Add Specific Privilege** → role **readWrite**, database
     `cis`, collection empty. Don't pick "Atlas admin" or "Read and write to any database".
   - **Add User**.
5. **Connection string:** **Clusters** → **Connect** on the `ieee-cis-app` cluster → **Drivers** → Node.js. Copy the string
   that looks like `mongodb+srv://cis-app:<db_password>@ieee-cis-app.abcde.mongodb.net/?retryWrites=true&w=majority&appName=ieee-cis-app`
   and replace `<db_password>` with the password from step 4. (The autogenerated password uses only letters and
   numbers. If you ever set one with `@ : / ? # [ ] %` in it, those characters must be URL-encoded.)
   Save the finished string in the password manager as **MONGODB_URI**.
6. **Network access:** leave it empty for now. Render's addresses are added in step 2.5. Never add `0.0.0.0/0`
   ("allow access from anywhere").
7. **A second owner for handover:** **Project** → **Access Manager** → **Invite to Project** → the faculty
   coordinator or next web lead as **Project Owner**.

## 2. Render (the admin server)

1. Sign up at <https://dashboard.render.com> with the club email, then connect GitHub when asked. Give Render access
   to **this repository only**.
2. **Create the service from the Blueprint** (easiest): **New** → **Blueprint** → pick the repository → branch
   `main`. Render reads `render.yaml` and shows one free web service, `ieee-cis-admin`, in Singapore. It asks for
   these values:

   | Setting | What to enter |
   |---|---|
   | `MONGODB_URI` | The connection string from step 1.5 |
   | `SITE_ORIGIN` | The website's address exactly, with no slash at the end, for example `https://ieee-cis-rec.vercel.app`. If you don't know it yet, enter the address you expect and correct it after step 3 |
   | `EXPORT_TOKEN` | A new random secret (see below). Save it: Vercel needs the same value |
   | `IP_HASH_KEY` | Another new random secret |
   | `SETUP_TOKEN` | Another new random secret. Save it: you need it once, in step 4 |
   | `DEPLOY_HOOK_URL` | Leave empty for now (step 3.6) |

   `NODE_VERSION` (24) and `MONGODB_DB` (`cis`) are already filled in by the Blueprint.

   **Random secrets** must be at least 32 characters. Make each one with the password manager's generator (40+
   letters and numbers) or on a computer with Node installed:
   `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`.
   Use a different value for each.

   Click **Apply**.

   *Without the Blueprint:* **New** → **Web Service** → the repository → Language **Node**, Branch `main`, Region
   **Singapore**, Root Directory empty, Build Command `npm ci`, Start Command `node backend/index.ts`, Instance Type
   **Free**. Under **Advanced** set Health Check Path `/healthz`, and add every setting in the table plus
   `NODE_VERSION` = `24` and `MONGODB_DB` = `cis`.
3. Wait for the first deploy to finish. The logs show `server_started`. Note the service address at the top of the
   page, for example `https://ieee-cis-admin.onrender.com` (Render adds a suffix if the name was taken).
4. Open `https://<service>.onrender.com/healthz`. It should say `ok`. Then open
   `https://<service>.onrender.com/api/health?db=1`. It says `"db":"down"` for now, because Atlas doesn't let Render
   in yet.
5. **Let Render into Atlas:** in Render, open the service → **Connect** (top right) → **Outbound** tab. Copy each IP
   range. In Atlas → **Security** → **Network Access** → **Add IP Address**, paste one range, comment
   `Render Singapore` → **Confirm**. Repeat for every range.
6. Open `https://<service>.onrender.com/api/health?db=1` again. After a minute it should say `"db":"up"`.

## 3. Vercel (the website)

1. **Point `/api` at Render.** In `vercel.json` in the repository, replace `REPLACE-WITH-RENDER-SERVICE` with your
   service's name from step 2.3, so the line reads
   `"destination": "https://ieee-cis-admin.onrender.com/api/:path*"`. Commit and push to `main`. (Claude can do this
   for you; the address isn't secret.)
2. Sign up at <https://vercel.com> (Hobby) with the club email and connect GitHub. Hobby can only import repositories
   owned by a personal GitHub account, not by an organisation.
3. **Add New** → **Project** → import the repository. Framework Preset **Vite** (detected); leave Root Directory,
   Build Command and Output Directory as they are — `vercel.json` already sets them (the site is built from
   `frontend/`). Open **Environment Variables** and add:

   | Name | Value |
   |---|---|
   | `CONTENT_EXPORT_URL` | `https://<service>.onrender.com/api/export/published` |
   | `CONTENT_EXPORT_TOKEN` | Exactly the same value as `EXPORT_TOKEN` on Render |

   Neither name starts with `VITE_`, so neither ever reaches visitors' browsers. Click **Deploy**.
4. **Node version:** project → **Settings** → **Build and Deployment** → **Node.js Version** → **24.x** → **Save**.
5. **Branch:** **Settings** → **Git**: Production Branch `main`. Leave **Automatically expose System Environment
   Variables** on (the build uses `VERCEL_PROJECT_PRODUCTION_URL` for its fallback).
6. **Rebuild link for Publish:** **Settings** → **Git** → **Deploy Hooks** → name `publish`, branch `main` →
   **Create Hook**. Copy the link. In Render → the service → **Environment** → set `DEPLOY_HOOK_URL` to that link →
   **Save Changes** (Render restarts the server). Treat the link like a password: anyone who has it can start builds.
7. **Check the address:** **Settings** → **Domains** shows the site's address. `SITE_ORIGIN` on Render must match it
   exactly (https, no slash at the end). Fix it in Render if needed.
8. **Deployments** → the latest one → **⋯** → **Redeploy**, so the build runs with the settings above. Nothing is
   published yet, so the build log shows `WARNING: nothing is published in the admin yet` and then uses the content
   in `frontend/src/data`. That is expected for this first build.

## 4. Your owner account

There is exactly one owner account (the web lead). Everyone else is an editor.

1. Open `https://<site>/admin/setup/owner#<SETUP_TOKEN>`: the site's address, then `/admin/setup/owner#`, then the
   `SETUP_TOKEN` value from step 2.2. The part after `#` stays out of every server log.
2. Choose a username, a name and a passphrase. Because this account is handed to the next web lead each year, a role
   name works best, for example username `weblead` and name `Web lead`. The passphrase needs at least 15 characters;
   four or five random words are easy to type and strong. Save it in the password manager. You type it only in the
   browser, never in a chat. Click **Create account and sign in**.
3. **Remove `SETUP_TOKEN`** in Render → **Environment** (delete the row) → **Save Changes**. The admin reminds you
   until you do. Each value only works once anyway.

If you ever lose the owner passphrase: add a *new* `SETUP_TOKEN` value in Render, open the same link with the new
value, choose a new passphrase, then remove `SETUP_TOKEN` again.

3. The Publish panel shows "Rebuilding the site (1–3 min)" and then "Live". The Vercel build log shows

4. **Accounts** → **Backups** → **Download backup**. Save the file to the club Drive.
5. **Accounts** → **Invite someone** for each office bearer. Send each one-time link privately. Links expire after

## Running everything on your computer

You need Node.js **22.18 or newer** (24 recommended), because the admin server and the build script are TypeScript
files that Node runs directly.

```bash
npm install                  # one install for all three projects (frontend, backend, shared)
cp .env.example .env.local   # then fill it in (it is never committed)
npm run server               # terminal 1: the admin server on http://localhost:8787 (reads .env.local)
npm run dev -- --port 5175   # terminal 2: the site on http://localhost:5175; /api goes to the admin server
```

- **Database for local tests:** Atlas only accepts listed addresses. In Atlas → **Network Access** → **Add IP
  Address** → **Add Current IP Address**, tick **This entry is temporary** and choose a few hours. Remove it when
  you're done.
- **Keep test data out of the real content:** in Atlas, give `cis-app` a second privilege, **readWrite** on database
  `cis-dev`, and put `MONGODB_DB=cis-dev` in `.env.local`. Without that, local tests change the live content.
- **A local owner:** set `SETUP_TOKEN` in `.env.local`, restart `npm run server`, and open
  `http://localhost:5175/admin/setup/owner#<SETUP_TOKEN>`.
- **Without a database** (`MONGODB_URI` empty) the server still starts; the admin says no database is connected.
- **Publishing locally** saves a release but doesn't rebuild anything (no `DEPLOY_HOOK_URL`). `npm run dev` keeps
  showing the files in `frontend/src/data`. To bake the published content into a local build, run
  `CONTENT_EXPORT_URL=http://localhost:8787/api/export/published CONTENT_EXPORT_TOKEN=<EXPORT_TOKEN> npm run build`.
  This overwrites `frontend/src/data/*.json` and adds photos to `frontend/public/images`; don't commit those changes
  (`git restore frontend/src/data frontend/public/images` undoes the edits and `git clean -n frontend/public/images` lists the added photos).
- **Checks:** `npm run lint`, `npm run test:server` (no database needed) and `npm run build`.

## What each setting does

| Where | Setting | Purpose |
|---|---|---|
| Render | `MONGODB_URI` | The Atlas connection string (`cis-app` user) |
| Render | `MONGODB_DB` | Database name, `cis` |
| Render | `SITE_ORIGIN` | The website's address. Changes are only accepted from pages on it, and invite links point to it |
| Render | `EXPORT_TOKEN` | Lets the Vercel build read the published content. Same value as Vercel's `CONTENT_EXPORT_TOKEN` |
| Render | `DEPLOY_HOOK_URL` | Vercel's rebuild link, called after every Publish |
| Render | `IP_HASH_KEY` | Stores visitors' IP addresses only as pseudonyms in the activity log |
| Render | `SETUP_TOKEN` | One-time owner setup or recovery. Remove it after use |
| Render | `NODE_VERSION` | `24` |
| Vercel | `CONTENT_EXPORT_URL` | `https://<service>.onrender.com/api/export/published` |
| Vercel | `CONTENT_EXPORT_TOKEN` | Same as Render's `EXPORT_TOKEN` |

**Changing a secret:** for `EXPORT_TOKEN`, change it on Render and Vercel together. For the deploy hook, delete it
in Vercel, create a new one and paste it into Render. For the database password, reset it in Atlas → **Database
Access** → **Edit**, then update `MONGODB_URI` on Render.

## How a build gets its content

Every Vercel build first runs `frontend/scripts/fetch-content.ts`:

1. It asks the admin server for the published content, retrying for about 3 minutes while Render wakes up.
2. It checks every section with the same rules as the admin. If anything breaks a rule, the build stops with a list
   of the problems, and Vercel keeps the current site online.
3. It downloads only new or changed photos, checks each one, and writes `frontend/src/data/*.json`, the photos,
   `/content-snapshot.json` and `/content-version.json` (the release the admin waits for after Publish).
4. If the admin server can't be reached, it copies the content that is live right now from the site's own
   `/content-snapshot.json`, so a code change can still go out and content never goes back to old files. Only the
   very first build, when the live site has no snapshot yet, uses the repository's `frontend/src/data`.

So after go-live, editing `frontend/src/data` in GitHub doesn't change the live site. Use the admin.
